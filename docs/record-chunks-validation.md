# 無損失レコード分割の実装・検証

既存の所有者限定RPCだけで大きな学習計画と画像ノートを同期する。ローカル実装済み、未公開。本番のDB・Storage・権限・資格情報は変更していない。

## 保存と送受信

- 200 KiBのUTF-8断片をbase64で既存localStorageコレクションに送る。断片のヘッダー込みでも従来の900 KiBバッチ上限とサーバー上限内に収める。ガードと全断片の受領確認まで親を送らない。
- 原文はlocalStorage、categoryNotes、logicalRaw、復旧用原本に保持する。準備中に操作IDや原文が変わった場合は最新内容を再確認する。凍結済みの未確認要求を変更しない。
- 受信は各断片・親ID・全体のハッシュ、サイズ、個数、復元後の計画／ノート形式を検証した後、既存の原子的トランザクションで反映する。不完全な版は既存データを置き換えず、手動再試行で断片を再取得する。
- 更新・削除・競合選択で不要になった断片は、親の受領確認後にだけ削除要求へ変換する。再送中の要求があるときは掃除しない。
- 新版の計画一覧・ローカル再捕捉・通常のバックアップには断片とガードを含めない。Snapshotと断片付きバックアップは原文へ復元してから従来の検証・取り込みを行う。Snapshot全体32 MiBの既存上限は維持する。
- 競合の比較と原本書き出しでは、両方の完全な原文を保持する。送信形式はCASのため別途保持する。

## 自動テスト

tests/record-chunks.test.mjsは既存SQLをPGliteで動かす。695問の有効な計画、復号可能な大きなPNG、二端末、再起動、失われた受領応答、送信前オフライン、途中編集・削除、競合と原本書き出し、欠損・改ざん、準備／受信時のQuotaExceededError、接続境界、削除を検証する。

local-storage-recordsとstudy-plan-storageでは、分割後の再捕捉で再送ループが起きないことと、実際のバックアップ取り込み・書き出しで計画とPNGが保全されることを検証する。全体テスト423件とTypeScript／productionビルドが通過した。空のPullの自己再送ループ修正も維持する。

## 旧クライアント

公開SHA e57523d73dde9eb68133d4abdaf4648ae03a474dと同一ソースツリーの旧エンジンをfake IndexedDBで実行した。計画分割・ノート分割の双方でガードをステージ保存前に拒否し、既存の原文を保持する。旧Snapshot検証も拒否する。

旧版での継続同期はできない。更新後に再開する仕様。過去の全版での互換性を保証するものではない。

## 実画面と未検証範囲

スマホQAはローカルのproductionビルド、実UIボタン・実IndexedDB、合成695問計画と合成PNGを使う。すべてのクラウド要求を横取りし、360／390px、同期完了、再読み込み、別端末相当の復元、既存の演習資料画面でのPNG描画、閉じる／再表示の7ケースを確認した。

本番の実アカウントや実端末の通信は未検証。Libraryの実データ取得はWindowsの公式helperのos.setxattrエラーで阻まれており、別経路のダウンロードはしていない。合成データの完全一致検証と実データの確認を区別する。

実行ログ・画面・ハッシュは作業領域qa/oversized-recordに保存する。QA用ビルドは無効なplaceholder公開キーを使用しているため、公開対象ではない。
