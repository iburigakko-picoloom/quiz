# QuizMake 全体同期65%停止の調査と修正

2026年10月9日の調査。指定リポジトリと既存originのmainは、いずれも `4aaf913119b717c1a89dd64f5dd9ee2cc3f31676`。公開ページの `build-info.json` とHTMLも同じcommitだった。既存の未コミット変更を保持し、開始時の追跡済み差分を `tmp/whole-sync-preexisting.patch` に退避した。本番DB・Storage・学習データは変更していない。

## 確認した原因

16/16件は、ペイロードに含まれるPDFファイルレコードの処理件数であり、資料参照や画像・完全バックアップの検証完了ではない。元の `wholeSyncIncoming.ts:37` はPDF受信後の段階を更新せずに完全バックアップを生成していた。`syncAttemptStatus.ts:12` の資料受信範囲が50〜65%なので、その後の例外でも16/16件・65%が残る。

本番は読み取り専用の集計で確認した。本文、資料名、問題ID、ユーザーID、同期ID、トークン、URLは出力していない。

| --- | ---: |
| 現在revision | 264 |
| 保存時刻 | 2026年10月8日20時35分58秒 日本時間 |
| PDFファイルレコード／資料一覧のPDF | 16／16 |
| 欠けたPDFファイルレコード／Storageオブジェクト | 0／0 |

| 資料参照総数 | 8,989 |
| どの資料一覧にも存在しない資料IDへの参照 | 460 |
| 登録資料はあるがページIDがない参照 | 0 |

460件の参照不整合は、元の `backupPayload.ts` の `materialIssues` が検出する条件に該当する。PDF取得がすべて成功しても、元の `validateFileBackup` の完全性検査（同commitの128行目）で停止する。同じ条件を合成データで再現した。

元の例外経路は `buildWholeIncomingFile` → `createCompleteFileBackup` → `validateFileBackup` → `createFileBackup` が例外化 → `wholeSyncEngine.ts:201` が `invalid_response` に包む → `observeRecordSyncAttempt` → `syncFailureReason` → `SyncStatus`。完全性検査の共通文「画像・PDF・資料が不足」にPDFが含まれ、元の `syncStatusReason.ts:10` が画像不足や資料参照不整合も「クラウドのPDFを読み込めません」と分類していた。画像本体不足でも同じ誤表示になることを回帰テストで確認した。

別の実装不具合も確認した。元の `backupPayload.ts:39` は、クラウド由来の画像部分コピーを作る際に `getNoteBackupIssues` を呼ぶ。この関数が参照する保存一覧は現在の端末のノートmanifestであり、受信側の一覧ではない。両側のノート構成が異なるだけで「PDF・ノートを完全に確認できません」と失敗する。端末のみにあるノートを持つmanifestと正常な受信側を使って再現した。

23時46分の実機例外ログと実機が保持していたrevisionは未取得であり、その瞬間の単一原因の確定とは区別する。確認した460件の不整合は同じ停止条件を直接満たす。各PDFの実バイト列は本番から取得していないため、SHA-256や当時の通信結果は未検証。参照不整合が作られた操作履歴も未確定である。現行の入力正規化は参照の文字列形状だけを検証し、存在する資料・ページとの照合をしていなかった。

## 実装した修正

| ファイル | 修正の意図 |
| --- | --- |
| `src/utils/syncDataIntegrity.ts` | 型付きエラーと、資料ID・ページID・所有セット・ファイル収録の純粋な整合性検査。診断は処理名・分類・件数・HTTP状態などに限定する |
| `src/utils/wholeSyncIncoming.ts` | PDF取得前に参照を検証。端末の同一PDFを必要なキーだけ読み、所有アカウント・サイズ・SHA一致を確認して再利用。受信後のバックアップ生成・検証段階を表示する |
| `src/utils/backupPayload.ts` | 画像不足、画像参照、PDF不足、資料参照、ノート形式を区別。受信コピーを他方のローカルmanifestで照合しない。端末のエクスポートでは従来のmanifest検査を維持する |
| `src/utils/wholeSyncEngine.ts` | 型付き不整合でも既存の明示選択へ接続。通常の小さい差分送信も、確定する全体グラフの資料参照を検査してから凍結する |
| `src/utils/materialCloud.ts` | GETを最大3回、500／1,500msの待機で再試行。401・403・404・整合性不一致は繰り返さない。サイズとSHAは維持し、処理数・取得・キャッシュ・端末再利用を分類する |
| `src/utils/recordSyncCoordinator.ts` | PDF通信の前後でも既存のアカウント・接続先・保存ガードを実行する |
| `src/utils/syncAttemptStatus.ts` | 資料参照確認とバックアップ生成の段階を追加。永続的な不整合は停止し、型付き診断を失敗状態に保持する |
| `src/utils/syncStatusReason.ts` と `syncFailureDiagnostic.ts` | 新経路ではエラーコードで原因を決定。旧混合エラーもPDFだけに分類せず、安全な定型文を使う |
| `src/components/SyncStatus.tsx` | 主画面の短い理由と停止段階、詳細の処理・分類・HTTP状態・件数。配色・レイアウトの構成を維持する |
| `src/utils/syncService.ts` | 戻り値に型付き分類と安全な診断を保持する |
| `tests/whole-sync-incoming.test.mjs` と補助fixture | 16件後の失敗、誤分類、参照不整合、通信、検証、キャッシュ、制限ヒープでのPDF処理 |
| `tests/whole-sync-engine.test.mjs` | 失敗・再試行・両側の明示選択・原本保存の統合検証 |
| `tests/sync-rpc.test.mjs` と `package.json` | 旧文字列期待をエラーコード・SHA／サイズ分類へ変更し、通常検証と同期検証に新テストを登録 |

HTTPの待機・再試行は一時的な取得失敗に限定する。元の120秒の通信期限、50 MiB／ファイルの制限は増やさない。ストリームが登録サイズを超えた場合、短い場合、SHA不一致の場合は未完了PDFとして拒否する。中断したアカウントや接続先のガードを通信エラーへ読み替えて再送しない。

PDFは既存どおり順に処理する。全体受信では端末内のPDFを一括エクスポートせず、必要なファイルだけ遅延読込する。検証済みメモリキャッシュと一致すれば、端末側の再読込も行わない。既存のダイジェストキャッシュ上限48 MiB文字数、PDFキャッシュ上限24 MiB文字数を維持し、25 MiBの同一PDFを再ハッシュしない性能を維持する。完全バックアップ形式自体は変えず、巨大な集約バックアップの実機メモリ上限は残る確認事項とする。

## データ保護と復旧

不整合の参照は削除・置換・推測せず、そのまま保持する。受信中の検証失敗では端末へ反映せず、送信側では未完成グラフを凍結・公開しない。従来の所有者確認、SHA、全件読取、バックアップの保存と読み戻し、CAS、revision、編集世代、Outbox、operationIdを維持する。

通常の同期で完全性を通過すること、明示選択時は選んだ側を検証し、もう一方の原本を保管・読み戻すことを維持する。旧画像だけの限定的な部分コピーは引き続き認めるが、PDFやノートの欠落へ例外を拡大しない。受信側のノートをローカルmanifestで誤判定しなくなっても、端末原本の退避とノートの形式・収録数・ハッシュ検証は省略しない。

現在の460件は、存在する資料IDとページIDを確定する情報がないため自動修復していない。健全なデータを持つ端末がある場合は、同期画面でその端末側を明示選択する。不整合のあるクラウド原本を保管・読み戻した後にだけ置き換える。クラウド側が不整合のままなら、クラウドを選び直しても安全に停止する。

両側が不整合なら、先に原本・バックアップを保管し、資料を保存した元端末・バックアップと照合する。正しい資料・ページの対応を確認してから紐づけを修復する。参照削除、ページ番号からの推測、PDF再登録だけで旧参照が直ったとみなすことは行わない。今回本番の460件に対する修復操作は実施していない。

## 検証結果と境界

新規テストでは以下を確認した。

- PDF16件が成功し、その後画像本体不足で失敗するケース。元の表示誤分類を固定fixtureで再現し、新表示は画像不足とする。
- 16件以外のPDF本体欠落、資料ID欠落、画像メタデータ欠落、ノート形式不整合。永続的な不整合は自動再試行しない。
- HTTP401／403／404／500、タイムアウト、通信切断、サイズ・SHA不一致、一時失敗からの回復と再試行の上限・待機時間。
- ローカルノートmanifestと受信側が異なる正常ケース。端末側の欠落検出は継続する。
- アカウント変更、正確な端末PDF再利用、他所有者の拒否、PDF後の実段階表示、成功確定後だけ100%になること。
- 192 MiBのJSヒープ制限で4 MiBのPDF4件を処理し、同時ダウンロードが1件で、完全バックアップが検証できること。
- 実SQLを使う隔離した全体同期で、失敗直後と再試行後のローカル・クラウド・Outboxを照合。不整合側の明示選択は停止し、健全側の明示選択後は不整合原本がバックアップに残ること。

既存テストの双方変更、revision変更、端末編集、原本保存容量不足、応答喪失と同一UUID再送、旧画像の限定救出も維持する。`npm run test:sync` は162件成功、`npm test` は647件成功、失敗はいずれも0件。`npm run build` は全体同期ON設定で成功。既存のチャンクサイズ・動的import警告は残る。

配信ワークフローは `VITE_WHOLE_SYNC_ENABLED=true`。未設定のローカル環境ではこのゲートがOFFになるため、最終ビルドは同じON設定で検証する。公開ページはmainと同じcommitだったが、23時46分の実機がPWAキャッシュやネイティブビルドのどれを使ったかは未確認。

実機のiOS／Android、実回線の当時の失敗、PDFの本番実バイト列、実機キャッシュ、最大容量でのモバイルメモリは未検証。新しい失敗診断は認証情報・本文・署名付きURLを出力せず、処理段階、分類、件数、HTTP状態を確認できる。

今回の同期修正にDB migrationは不要。ステージングで修正フロントエンドをON設定で確認してから配信し、実機の配信commitと更新状態を確認する。同じ作業ツリーの公開機能・グループUIの未適用SQLは別の変更であり、この同期修正のために一括適用しない。
