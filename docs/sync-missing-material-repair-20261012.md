# 同期停止の調査と修正（2026-10-12）

## 確認できた原因

- 実機の失敗は `backup / material_reference`、`exportFileBackup / local_backup_validate`。8989参照のうち460参照が、端末の資料一覧に存在しない同一資料IDを指していた。容量使用量は約458MB / 10.7GBで、今回の原因を容量不足とは判定できない。
- 本番の読み取り専用調査で、旧資料所有セットの資料索引・PDFレコードには削除記録があり、コピー先には同じ資料を保全復旧した索引・PDFレコードが存在することを確認。クラウドでは当該460参照すべての資料・ページが存在する。端末にはまだ届いていない。
- `public.quiz_sync_read` は所有者チェックとロック後、`private.quiz_sync_materialize_snapshot` で全件を再構築する。旧実装は各コレクションをJSONBに再解析し、成長するAppDataを繰り返し連結していた。本番の読み取り専用EXPLAINでは約7154ms。実機ではSQLSTATE 57014 / HTTP500で10秒制限を超えている。
- 資料の原所有セットが削除された経緯は、現在のコードだけでは実機操作まで確定できない。現在は参照先資料を持つセットの削除と、参照切れのコピー保存を防止済み。既存端末に残った欠落資料の復旧が必要だった。

## 修正

- `20261012000305_sync_snapshot_linear_assembly.sql`: 検証済みのレコードJSONテキストを一度組み立てる。返却仕様、並び順、設定、ノート、画像メタデータ、未移行Snapshot、所有者制限を維持。10秒制限の延長やデータ変更はしない。
- `materialReferenceRepair.ts`: 同じクラウド問題ID・セットID・資料ID・ページIDで証明できる欠落資料だけを追加する。既存資料の変更、ページ推測、ノート救済、PDF検証の省略は行わない。所有者・サイズ・SHA-256検証は既存のPDF転送処理を利用する。
- 端末原本を保存・読み戻し・ダイジェスト検証してから、資料索引・検証済みPDFキャッシュ・送信用の小さな参照レコード・Outboxを同一IndexedDBトランザクションで記録する。アカウント、端末コミット、クラウドrevisionを再確認する。
- `wholeSyncEngine.ts` / `recordSyncCoordinator.ts`: 原本比較の前に限定復旧を接続。復旧後は以前の比較結果を使わず、次の同期で通常のCAS・競合選択をやり直す。どちらかの教材全体を自動選択しない。

## 検証

- 1万問の旧新Snapshot内容一致、Unicode/引用符/改行、並び順、設定、資料、画像、所有者制限。
- 460参照と16資料のうち、不足1資料だけを復旧。15資料、問題、学習記録を保持。検証済みキャッシュ再利用、再実行時の重複なし。
- 別問題・ページ不一致・既存PDF衝突・別アカウントは復旧しない。
- 通信内容破損、容量不足、revision変更、原本保存失敗時はライブ資料・Outboxを変更しない。
- 同期関連185テスト、公開候補の全体729テスト、公開用ビルドに成功。

## 本番適用

SQLはユーザーの具体的承認後にトランザクションで関数変更とマイグレーション記録を適用し、既存レコード・revisionに変更がないことと読み込み時間を再確認する。実機の端末データは直接操作できないため、配信後の再試行と診断確認が必要。
