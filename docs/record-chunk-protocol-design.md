# 既存の権限内で行う無損失レコード分割

分割処理は実装済みで、SQLテストと実画面検証をローカルで行った段階。未公開。本番のDB・Storage・権限設定は変更していない。実装と検証範囲は[検証記録](record-chunks-validation.md)を参照。

## 適用対象と権限

学習計画などの localStorage と、画像を含む indexedDbNotes の大きな原文を扱う。既存の所有者限定レコード RPC の localStorage コレクションに断片を格納し、新しい Storage bucket、公開URL、サービスキー、RLS権限を追加しない。900 KiB のクライアント上限、1 MiB のサーバーバッチ上限は維持する。

## 原文と送信形式

- 端末の localStorage・categoryNotes・バックアップには、完全な原文を保持する。
- 同期レコードの親は原文の代わりに版マニフェストを送信する。ローカルレコードには、送信形式とは別の logicalRaw を持たせ、取り込み・保存時の比較で原文を再生成・再送し続けないようにする。
- 断片は親キーのハッシュ、内容全体の SHA-256、断片番号を含む別キーを使う。UTF-8 の原文を一定のバイト数で分割し、base64 で送信する。UTF-8 の途中で切れても、全体を結合してから復号するため文字を失わない。
- マニフェストはスキーマ、対象コレクション・ID、内容版のハッシュ、全体バイト数、断片個数、各断片ハッシュを固定する。
- baseContent と CAS の比較は、サーバーが受け取った送信形式を維持する。編集中の画面や学習計画の分母・内容版を変更しない。

## 順序と原子的反映

互換ガードと全断片の受領を確認してから、親マニフェストを確定・送信する。凍結済みで応答未確認のバッチの本文・operationId は変更しない。事前準備、凍結、受領後の更新はいずれもトランザクション単位で行い、途中編集の原文を古い準備結果で上書きしない。

受信は、ステージと既存の断片から対象版を集め、個数・各断片・結合後のサイズ・全体ハッシュをすべて検証する。完全に検証できた親だけ、元のデータと一緒に原子的に反映する。欠けた版や不正な版で既存の計画・ノートを消したり、部分状態を達成として扱ったりしない。断片だけが先に届いても画面の原文を置き換えない。

Snapshot からの読込・復元でも、通常のデータ検証と取り込みの前に同じ復元処理を通す。内部の断片・互換ガードは、計画一覧や端末設定の項目として反映・再捕捉しない。

## 旧クライアント

計画の親マニフェストは従来の計画パーサーでは不正になるが、ノートだけの場合も安全に停止する必要がある。分割形式が使われる同期先には、従来の計画検証で拒否される専用の互換ガードを先に送信する。新クライアントはガードを同期内部レコードとして扱う。

公開済みの旧パーサーで実際に拒否されること、拒否前に画面データが書き換わらないこと、旧クライアントの応答未確認の送信が CAS と冪等性を維持することを検証する。旧版での同期継続ではなく、データを保持した更新要求を互換性の基準とする。すべての過去版に対する安全性を検証したとは主張しない。

## 削除と検証

親の削除を確認する前に、その親が参照する断片を削除しない。途中で再編集された親、ほかの版、再送中の要求が参照する断片を清掃対象にしない。不要な断片の保全・削除順序は、再起動とバックアップ復元を含めて検証する。

検証は、有効な695問の計画と画像ノートの完全一致復元、欠落・破損・重複断片、途中編集、複数端末競合、原子的反映失敗、応答消失・再起動・再送、削除順序、別アカウント、旧版、Snapshot復元を含む。同期成功は保存済み原文とサーバー受領を確認してから記録する。
