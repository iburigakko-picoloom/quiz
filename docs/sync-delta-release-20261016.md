# 同期・保存領域の段階導入（2026-10-16）

通常保存は項目単位の送信待ちを作り、PDF・画像の転送は独立した再開可能キューで処理する。新方式の競合順序はサーバー確定順であり、固定操作IDの再送で順位は変わらない。

## 旧データの引き継ぎ

- 既存のレコード、削除記録、確定Revisionをそのまま利用する。サーバー移行は既存本文を書き換えない。
- 旧送信の受領結果を確認した後、固定Revisionのチェックポイントを分割受信・検証する。確認済みのチェックポイントからのみアカウントの同期領域を切り替える。
- 初回取得でクラウドと異なる未確定の旧原本は復旧候補として保存する。古い控えを現在日時の編集として自動送信しない。
- 取得済みPDFが表示用ノートにだけ残っている場合、その原本を退避し、ハッシュ一致を確認してオフラインでも再利用する。
- Blob移行は本文保存、読み戻し、SHA-256照合の後に参照を切り替える。処理中・未送信・救出対象は自動整理から除外する。旧領域の現在版と控えを両方検証するまで削除しない。
- 更新後の旧アプリからの書き込みは `update_required` で停止する。新方式から旧方式への自動後退は行わない。

## 公開ゲート

1. 救出原本の保護と検証済みクライアントを公開する。`VITE_DELTA_SYNC_ENABLED=false`。
2. 互換性を保つサーバーAPIと専用Blob保管庫を追加する。全ての既存同期領域の `delta_enabled` は false のまま。データ件数・内容ハッシュが変更前と一致することを確認する。
3. 検証済みクライアントのフラグを有効化して公開する。各端末が自分の未確定送信とチェックポイントを確認した後に切り替わる。障害時は原本を残して同期を停止し、端末保存を続ける。

## 検証結果

- 公開用作業ツリーの関連テスト136件成功。型検査・本番ビルド成功。
- 移行中断、容量不足、アカウント変更、旧送信APIの停止、回答ID重複、確定後の応答消失、削除対編集、復旧原本の保持、取り込み後の新PDF、完全バックアップの往復を検証。
- Windows WebKitの2ブラウザー領域、PDF合計524,288,000 bytesで回答10件を検証。回答処理によるPDF本文読み出し0回、完全バックアップ書き込み0回、最大RPC要求2,809 bytes。
- 応答消失後は受領記録から確認し、同じ操作を再適用せず回答11件・カウント11を保持。
- 50msの通信待ちを入れたローカルPostgres相当環境で、保存から同期完了までの10測定のp95は2,370ms。自動送信の1.5秒待機は含まない。本番回線・実機iPadでのSLOを証明する測定ではない。
- 本番移行前：39,494レコード、47,113,438 payload bytes、11同期領域。本文・位置・Revisionの集約ハッシュ `5cba22b4bd974f6cb8ac50a622c8c457`、旧Snapshotの集約ハッシュ `17ad84b09515e13a581a9a681a4252dd`。

## 本番照合

原本保護版 `20da277` のPages公開成功後、差分API・非公開Blob保管庫・明示的なアカウント削除用の所有者限定権限を適用した。適用後も39,494レコード、47,113,438 payload bytes、11同期領域、上記2種類の集約ハッシュが全て一致した。既存同期領域の新方式有効件数は0件のまま確認した。旧APIを迂回する内部関数は匿名・ログイン済みユーザーの双方から直接実行できない。

追加テストで、新方式の領域削除が既存の外部キーにより原本・差分・受領記録を正しく連鎖削除することを確認した。新Blobは更新不可で、通常の端末キャッシュ整理はクラウド原本を削除しない。明示的なアカウント削除時のみ既存のStorage API経由で本人のBlobを削除する。

セキュリティ・性能アドバイザーを確認。新規privateテーブルのRLSは直接アクセス拒否を意図したポリシーなし設定。新機能に対する警告レベルの指摘はない。既存機能に対する警告は今回の対象外。

端末の約3GBの削減量は未計測。保存内訳は移行前後の実測で評価し、削減量を推測しない。初回の旧データ照合・Blob変換は通常の小さな差分送信より時間がかかる。
