# 全体送信の小さな再開位置

各パーツの成功後に全送信本文を読んで比較・再保存していた処理を、既存の `appRecordMeta` に保存した小さな再開位置の更新へ変更しました。本文・パーツUUID・ダイジェストは一度保存した原本のままです。パーツ更新は同期先・送信ID・wireDigest・直前のcursorを照合します。新store、RPC、プロトコルは追加していません。

本文と再開位置は初回の同じトランザクションで保存します。確定・破棄・全体置換では両方を削除します。旧クライアントの本文内cursorはそのまま読み、次の成功パーツで小さなcursorを作るため、未確認の本文やUUIDを作り直しません。旧cursor、飛ばしたパーツ、異なるID・ダイジェスト・アカウント、不正cursor、保存失敗は再開位置を進めません。

## 約25MBの代表比較

2026-10-05、Windows / Node 24.17.0で、学習用ID・範囲・保存メタデータを持つ合成JSON 26,214,400 bytes（25 MiB）を同じ条件で比較しました。分割後は35,057,092 bytes、43パーツ、131レコードです。実際の計画内容の妥当性ではなく、大きなメタデータの保存・全体置換・再送境界を測るための合成値です。

| 測定項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 進捗更新の回数 | 43 | 43 |
| 進捗更新の論理書込量（JSON UTF-8） | 1,509,395,752 bytes | 13,106 bytes |
| 進捗・再開中の本文読込回数 | 49 | 6 |
| 進捗区間（計測用の書込量算出時間を除く） | 8,970.58 ms | 537.86 ms |
| 最初の原本保存 | 106.99 ms | 125.48 ms |
| 分割送信・再開・確定の全区間 | 16,986.17 ms | 5,536.98 ms |

進捗区間はパーツ成功の応答から次の送信呼出しまでで、3回の再起動時の原本読込・検証も含みます。書込量は保存する値のJSONサイズで、物理ディスク書込量ではありません。時間は単回比較で、実機性能の保証には使いません。

変更前後とも、最初のパーツが保存された後の応答喪失、20パーツ後の再起動、全パーツ確定後の応答喪失を再現しました。同じパーツUUIDと本文ハッシュで再送し、再起動3回の後に確定済み領収書から回復しました。クラウドの全パーツから元の25 MiB値を完全復元して照合しました。Outboxは確定後に消え、利用者の編集世代は増えていません。

`tests/whole-sync-large-progress.test.mjs` がこの代表ケースを必須テストに含めます。既存の受信・送信・保存の関連19件も通過しました。隔離したfake IndexedDBと、変更していない全体同期SQLを動かす直列PGliteでの確認です。実Auth、本番PostgreSQLの同時接続、実ブラウザーのディスクI/Oは未確認です。

新SQLの内容とSHA256は変更していません。[本番適用手順](whole-sync-rollout.md)の個別承認待ちで、SQLは未適用、公開の全体同期ゲートはOFFです。
