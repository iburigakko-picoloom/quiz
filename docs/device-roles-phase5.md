# Phase 5: 端末の役割と同期の整理

## 実装

- 基準: Phase 6 `f6dbbe6`。端末設定を同期画面の先頭に配置し、メイン/サブを選択する。既存の同期状態、競合選択、バックアップ・復旧、詳細設定を維持し、更新確認ボタンを追加。
- 既存の `AutoSyncController` の起動時 `checkRemote(true)` と送信キュー、復帰/オンライン/手動更新経路を再利用。サブでも回答・理解度・学習済み指定を保存・送信し、教材と進捗を受信する。
- メイン: 作成/取り込み/編集/PDF・手書き/資料管理/演習。サブ: 演習・進捗・受信。サブでは作成ナビ、フォルダ追加、教材操作を隠し、資料表示・編集導線と復元された編集ルートを制限する。
- 保存時にも内容変更を判定し、サブの教材変更を拒否する。回答だけの変更は教材を全走査しない。保存キュー内のデータロック取得後にもroleを再確認する。削除もデータロック内で検査。共有教材の取り込みや画像保存は処理開始時にも検査する。
- バックアップ復元・同期受信・明示的な端末データのリセットは復旧経路として利用可能。教材編集の制限によって復旧を不能にしない。

## 保存と移行

- 新規キー: インストール単位の `localStorage["quizMakeDeviceRole:v1"] = "main" | "sub"`。アカウント領域、同期対象プレフィックス、バックアップ対象に含めない。アカウント変更や別端末のバックアップ復元では役割をコピーしない。
- キー未設定の既存端末はメインとして従来動作を維持。破損・読み取り拒否はサブとして扱い、編集を許可しない。正常に保存できる環境でメインを明示選択すると回復できる。
- DB・RPC・RLSの追加変更なし。既存問題・PDF・ページID・手書き・共有・学習履歴の移行不要。
- 役割切替はroleキーだけを書き、保存データ・同期ID・端末ID・送信待ち・バックアップ・同期カーソルを変更しない。書き込み確認が失敗したら以前の設定へ戻す。
- 端末役割は操作設定でありアクセス権ではない。アカウント全体で唯一のメインを強制するものではなく、既存端末間の競合検知を維持する。排他的なメイン端末を導入する場合はオフライン編集・端末紛失・権限移譲を含む別のサーバープロトコルが必要。

## 切替と復旧

1. 編集/演習画面が共有Web Lockを保持。役割切替は同じLockを排他取得し、ほかのタブの編集中は拒否。編集画面はLockを取得してから表示する。
2. 同期ネットワークのLeaseを取得し、問題・ノートの保存完了を待つ。
3. 既存のorigin-wideデータロック内で、アカウント接続状態、送信待ち、競合、受信途中、資料転送、復旧候補、移行エラーを再検査。解決が必要な場合は切り替えない。
4. 別タブでデータが更新され画面が古くなった場合は既存のepoch検証が拒否する。画面を再読み込みして最新データを読み、再試行する。
5. 通信失敗は既存の再試行/更新確認、競合は既存の選択画面、破損はバックアップ・復旧へ進む。役割変更はこれらを回避するリセットとして動作しない。

## 大容量データを除外しない理由

現行モデルはPDF/画像の記述子と本文・ページ参照・手書きを一体として検証する。サブ端末だけ本文を欠落させると、未受信と削除を区別できず、整合性エラーやtombstoneの誤送信につながる。今回は全資料を保持する。将来の部分同期には明示的な未取得状態、オンデマンド取得、削除の所有権、バックアップ完全性、オフライン時の表示の設計が必要。
